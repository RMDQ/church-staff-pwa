# 服事表图片转 JSON 的 prompt（模板）

**这是模板，不要直接用。** 里面的 `{{...}}` 要由
`scripts/build-import-prompt.py` 从 Firestore 填进去，产生的成品会写到
`.local/`（已 gitignore）。

这个 repo 是公开的，所以同工姓名、绰号对照一律不写在这里。
下面范例里的人名都是虚构的。

## 怎么用

**在 app 里按「JSON 汇入」→「从照片辨识」，选服事表照片就好。**
辨识结果会填进下面那个文字框，看一眼再按汇入。

app 送到 `POST /api/roster/import-image`，那支
（`functions/api/roster/import-image.js`）组出 prompt，连照片一起送给
Gemini，把结果原样回传。**它不做任何验证** —— 名字比对、日期范围、汇入结果
那份报告全都还在 `parseRosterImportJson`，也就是手动贴上走的同一条路。
辨识只是省掉打字，不是另一条汇入流程。

### prompt 分成两半

| | 是什么 | 什么时候变 | 谁来填 |
|---|---|---|---|
| **模板** | 版面规则、栏名对照、绰号、敬拜团展开 | 有人去改 `.local/import-rules.json` 才变 | `--publish` 写进 `settings/import_prompts` |
| **现况** | 服事项目、活动清单、同工名单、今天 | 管理员在 app 里动一下就变 | worker **每次呼叫**现场读 Firestore |

所以 **新同工建完帐号就直接生效**，服事项目、活动选项新增也一样 ——
不必有人记得回来重跑脚本。

会这样拆是因为第一版把名单烤进发布的 prompt 里，结果每来一个新同工就要有人
记得跑一次脚本。没有人会记得。

### 只有改了规则才要重新发布

```
python3 scripts/build-import-prompt.py --publish
```

改了 `.local/import-rules.json`（版面规则、栏名对照、绰号）或模板本文之后跑。
**动名单、服事项目、活动选项都不用跑。**

`settings/` 的写入权限在 firestore.rules 里是 admin only，但这支脚本用的是
GCP 凭证（专案 editor 以上），走的是 IAM 那条路、不经过 rules。

模板里剩下的 `{{...}}` 必须刚好等于 worker 会填的那几个 —— 对不上的话脚本会
当场停下来，而不是发布一份带著 `{{NAMES}}` 字面值的 prompt 上去。

### 需要设定的东西

Cloudflare Pages 的**执行期**环境变数 `GEMINI_API_KEY`（见 `.env.example`）。
放错区会被编进前端 bundle，等于公开。

### 汇入前想先确认（人在这台机器前时）

```
python3 scripts/preview-roster-import.py <崇拜类别> <json 档>
```

这支会抓 Firestore 现况、产生一支暂时的 Dart 测试去呼叫 app 真正在用的
`parseRosterImportJson`，印出按下汇入会看到的结果 —— 哪些名字对不上、
哪几天不在范围内、每天的项目排序。跑完自动删掉那支测试。

## 在本机直接试 Gemini

```
python3 scripts/try-gemini-import.py youth 服事表.jpg --preview
```

跟 app 那条路用的是同一份 prompt 与同一个 parser，只是跑在本机，而且转完
立刻接上干式汇入。改了 prompt 规则之后要验，用这支比开浏览器快。
需要 AI Studio 的 key，放 `.local/gemini-api-key` 或 `GEMINI_API_KEY`。

差别只有一个：它用 `.local/` 那份本机填好的，app 用的是 Firestore 上发布过的
模板再现场填。填的逻辑两边各一份（Python 的 `fill_live`、JS 的 `fillPrompt`），
**输出必须一模一样**，否则本机验过的跟线上跑的不是同一份 prompt。

改完规则记得 `--publish`，不然只有本机是新的。

## 还有一条路：claude.ai

```
python3 scripts/build-claude-skill.py
```

产生 `.local/claude-skill/roster-import.zip`，上传到 claude.ai 的技能设定，
之后在那边附照片说「转 json」，把结果贴回 app 的汇入框。

app 内建辨识之后这条就不是主要流程了，留著当后路 —— Gemini 挂掉、额度用完、
或想换个模型看看结果差多少的时候还用得上。名单有异动一样要重跑再上传覆盖。

⚠ 不管哪一条路，送出去的都包含完整同工名单与整张服事表。AI Studio 免费层
Google 会用送进去的资料改善产品；付费层不会。上传到 claude.ai 也是同一个
判断题。

## 为什么要把名单填进 prompt

app 的姓名比对有三层。前两层是精确比对：先找一模一样的，找不到就找「名单里
以这个字串结尾、而且只有一个人符合」的。这两层错一个字就是查无此人。

中文名字常有罕用字，而那正是 OCR 最容易认错的地方。所以有第三层
（`_nearMatches`）：名单里只差一个字的那几位会被列出来当提示 ——
**但不会自动套用**。名字照表上原文写进服事表，uid 一个都不带。

### 为什么不自动接回去

拿真实名单量过（53 人）：

- 名单内部互相拼错一个字时，唯一对到「别的真人」的次数是 **0**。
- 但会落进这一层的几乎都是**还没建帐号的人** —— 新同工、外来讲员。
  而他们的名字常常跟某个真人只差一个字：表上写的人名单里没有，但名单里
  有个只差最后一个字的另一位，候选还唯一。

自动接的结果是：陈志豪的服事被记到陈志明头上、连上陈志明的 uid，提醒发给
陈志明，而「陈志豪」这个名字从表上整个消失。**两边都不会知道。**

所以第三层只提示。汇入结果会写成

```
名单里没有这个人
  ・陈志豪（名单里有很像的：陈志明）
```

要不要改那一格由人决定。**真正该做的还是让模型根本不要拼错字** ——
prompt 里附上完整名单当白名单，让它只能从里面挑。

**忘了重新产生也不会坏** —— 新同工不在名单里时，LLM 会照表格原文输出，
app 那边的后缀比对照样接得住。名单过期只会让**新来的那几位**退回旧模式。

## 模板本文

````
帮我把服事表照片转成 JSON。只输出 JSON，不要有任何说明文字，
不要用 markdown 的程式码围栏包起来。第一个字元是 [，最后一个字元是 ]。

## 只要这些

日期、服事项目、同工、活动。其他一律不要。
{{LAYOUT_RULES}}
## 服事项目命名

只能用以下名称，一字不差：
{{ROLES}}

清单里没有的栏位整栏不要输出。
{{EXTRA_ROLE_RULES}}

## 人名

**输出的人名必须是下面同工名单里的其中一个全名，一字不差。**
表格上写的是简称（去掉姓氏）或加了称谓，你要把它还原成名单里的全名。

同工名单：

{{NAMES}}

规则：

- 表格上的「小明」「小明哥」「陈小明」都要输出成「陈小明」。
  称谓有这些：哥／姐／姊／兄／弟／妹／弟兄／姊妹／牧师／传道／师母／
  长老／执事／老师／主任。「陈大明牧师」要还原成名单上的「陈大明」。
- 中文名字有很多罕用字，照片上可能看不清楚或容易认错。
  **不要自己拼字** —— 从名单里挑字形最接近的那一个。
- 一格有多个人就拆成多个元素。表格用「/」或「+」分隔的都算多人，
  例如「小明/大华」→ ["陈小明", "林大华"]。
- **people 照表格上写的先后顺序，不要重排**（不要照笔画、不要照名单顺序）。
  写在前面的通常是主要负责的人，app 会照这个顺序排每一周的名单。
- 空白格代表这一项还没排到人 → "people": ["待定"]。「待定」照写，不用对名单。
- 「暂停」不是人名，代表那周没有这一项 → 整个项目不要输出，
  不可以写成 ["暂停"]。
- 真的对不到名单里任何一位（例如新同工还没建帐号），就照表格原文输出，
  不要硬塞一个名单里的人。
{{NICKNAMES}}
{{TEAM_RULES}}
## 活动

放进该天的 `events`。哪些格子算活动，见上面「这张表怎么读」。

规则：

- 意思相同的话，优先用下面这几个既有名称，一字不差：
  {{EVENTS}}
- 对不到既有名称的就照表格原文一整串抄，**不要拆**。
  合并储存格里的「活动名称/地点」是一个名称，那个「/」不是分隔多人的意思。
- 同一天有多个活动就放多个元素；同一天不可以有重复的活动名称。
- **不要输出颜色。**
- 那一天没有任何活动的话，**整个 `events` 栏位不要写**（不要输出 `[]`）。

## 不要输出的栏位

- 表格下方的提醒、标题、经文、季主题。
- 表格下方那种「敬拜/某某、招待/某某」的负责人清单。那是各项的联络人，
  不是某一周的服事。

## 格式

[
  {
    "date": "2026-07-04",
    "duties": [
      {"role": "{{SAMPLE_ROLE_A}}", "people": ["陈小明"]}
    ],
    "events": ["夏令营/营地"]
  },
  {
    "date": "2026-07-11",
    "duties": [
      {"role": "{{SAMPLE_ROLE_A}}", "people": ["陈小明", "林大华"]},
      {"role": "{{SAMPLE_ROLE_B}}", "people": ["待定"]}
    ]
  }
]

- `date` 一定是 `YYYY-MM-DD`。不可以写 `2026/07/11` 或 `7/11`。
- 年份：标题有写就照它（例如「2026 年 7-9 月份」）。**标题没写年份的话**，
  今天是 {{TODAY}}，挑一个让表上那几个月份离今天最近的年份。
  年份猜错整份都汇不进去，而表上通常只有月和日，所以这条要特别小心。
- `people` 的每个元素都必须是字串。不可以出现 null、数字。
- `duties` 不可以是空阵列。那天完全没有服事就不要写 `duties` 这个栏位。
- 每一天至少要有 `duties` 或 `events` 其中一个，两个都没有就整天不要输出。
- 同一个日期只能出现一次。
- duties（服事项目）之间的排列顺序不重要，汇入后会自动照服事项目设定重排。
  但每一项里 people 的顺序很重要，见上面「人名」。

## 输出前自我检查

1. 每个 date 都是 YYYY-MM-DD，而且没有重复。
2. 每个 role 都在上面的命名清单里，一字不差。
3. people 里的每个名字都在同工名单里找得到一模一样的，或是「待定」。
   没有 null、没有数字、没有「暂停」、没有哥姐。
4. 没有空的 duties 阵列、没有空的 events 阵列。
5. 同一天的 events 没有重复的名称。
6. 输出的第一个字元是 [，最后一个字元是 ]，前后没有其他文字。
````

## 各崇拜的差异怎么设定

服事项目与活动清单由脚本从 Firestore 的 `settings/roster_templates`、
`settings/event_options` 读出来填入，不必手动维护。

各教会自己的规则放在 `.local/import-rules.json`，每个崇拜一个键：

```json
{
  "youth": {
    "layoutRules": "## 这张表怎么读\n\n一列一天，服事项目在最上面那一列。...",
    "extraRoleRules": "- 表格的「会前祷+奉献」是一栏，要拆成两项：会前祷告、奉献教导。\n  同一格的人两项都填。",
    "teamRules": "## 敬拜团\n\n敬拜团那一栏写的是团名，实际人员在表格下方的说明列。...",
    "nicknames": { "小名": "陈小明" }
  }
}
```

| 键 | 放什么 |
|---|---|
| `layoutRules` | **这张表的版面怎么读。** 见下一节 —— 这是三个崇拜差最多的地方 |
| `extraRoleRules` | **栏名 → 服事项目的对照表**，以及一栏要拆成两项之类的特例 |
| `teamRules` | 团名要展开成个别人员的规则 |
| `nicknames` | 跟本名没有共同字、只能查表的绰号 |

没有这个档案的话那几段都留空，其余照常产生。

### 为什么一定要写栏名对照表

`{{ROLES}}` 只说了「可以用哪些名称」，没说表上那一栏是哪一个。三张表的栏名
都跟服事项目名称不一样：

| 表上写 | 服事项目 | 哪张表 |
|---|---|---|
| 敬拜 | 敬拜主领 | 主日、儿主 |
| 讲道 | 信息 | 主日 |
| 导+录 | 导播（**一项**，服事项目里没有「控机」） | 主日 |
| 配唱 | Vocal | 儿主 |
| 木箱 | 鼓 | 儿主 |
| 会前祷+奉献 | 会前祷告 ＋ 奉献教导（拆两项） | 青崇 |

没有这张对照表，模型得自己猜「木箱」是「鼓」。猜错那一栏整个对不上，而且
**不会有人发现** —— app 只会说「没有设定这个服事」，看起来像是同工的设定
漏了，不像是整栏接错。

### 差一个罕用字的写法要写进绰号对照

表上写「雅亭」而名单上是「黄雅婷」、写「佳容」而名单上是「陈佳蓉」——
差的都是罕用字，而且去掉姓氏后只有两个字，后缀比对接不住
（`黄雅婷` 不以 `雅亭` 结尾）。第三层会把它们列成提示，但不会自动套用，
所以**这类要写进 `nicknames`**，让模型直接输出全名。

对不出来的就不要写。「佳芸」跟「陈佳蓉」（佳吻合）与「林淑芸」（芸吻合）
都只差一个字 —— 这种留给第三层把两个候选都列出来，由人决定。

名单里本来就可能有几组人互相只差一个字（兄弟姊妹、同一个名字字根）。
那几组的提示会一次列出两位，不挑。

### 为什么版面规则一定要各崇拜各写一份

原本这几条结构规则写死在共用的模板本文里，假设「一列一天」。实际上三张表
差到不能共用，而共用的版本对其中两张是**错的**，不只是不足：

- **主日是转置的** —— 日期在最上面那一列，服事项目在最左边那一栏。
  共用版本讲的「表格右侧时段栏位」「横跨多栏的合并储存格」在这张表上
  根本不是那个意思：跨多栏在这里是跨多个**日期**。
- **主日右边那块自己写了日期的活动要收进来**（「孩童奉献礼：11/29」），
  但共用版本有一条「格子里自己写了另一个日期的栏位整栏略过」，那是为了
  青崇的「周二祷告会」栏写的 —— 两张表对「自己带日期」的处理正好相反。
- **儿主的「回应」「小组」栏是整季合并成一格的**，意思是整季固定的分组，
  不是每周轮的服事，所以整栏不要。共用版本只有「横跨多栏＝常规服事被活动
  取代」，方向与语意都不对。

所以模板本文只留跟版面无关的部分（服事项目命名、人名还原、格式、自我
检查），版面那段换成 `{{LAYOUT_RULES}}`，各崇拜自己写。

## 活动颜色

prompt 刻意不输出颜色。颜色设在 app 的「事件选项设定」，名称一样就会自动套用。

不在事件设定里的活动还是会标上去，只是没有预设色，并列在汇入结果的
「活动没有固定颜色」。管理员可以在那一段直接按「加入活动清单」，颜色会
自动挑一个这个崇拜用得最少的；已经汇入的那几天也会跟著变色，不必重汇。

## 汇入后会看到什么

app 汇入完会跳出「汇入结果」。里面列的名字**都已经写进服事表了**，
列出来是让你知道，不是要你回去改 JSON：

- **没有设定这个服事** — 人在名单上，只是没设定这一项（临时支援很正常）。
  真的多了固定班底才需要按「新增服事至同工」。
- **外来讲员** — 只排在「信息」、名单里没有、也没有很像的人。名字照样写进
  去了，讲员没有帐号是正常的，所以一行带过，不算问题。名单里有很像的
  名字就不算讲员（多半是同工的名字被读错一个字），会留在下一段。
- **名单里没有这个人** — 名字有排上去，但没有帐号就收不到服事提醒。
  后面括号里的「名单里有很像的」是提示，**名字没有被换掉**。确定是同一位
  就把它加进 `.local/import-rules.json` 的绰号对照，下次汇入就会直接对上。
- **不确定是哪一位** — 名单里有两个人的名字都对得上，这一格没有连到帐号。
- **这几天没有汇入** — 服事表里没有那几天。app 只产生本季与下季。
  主日表旁边写在星期六之类的活动不会落到这里：主日的版面规则会把它放到
  活动之后最近的那个主日，名称后面带上它自己的日期（「感恩聚餐（12/26 六）」
  放进 12/27）。放之后是因为 app 只显示还没过的服事表，放在之前那个主日，
  活动当周就看不到了。
- **活动没有固定颜色** — 活动标上去了，只是没有预设色。管理员可以直接按
  「加入活动清单」。名称带著自己日期的一次性活动（「感恩聚餐（12/26 六）」）
  不会列在这里：名字每次都不同，加进清单也对不上下一次。
